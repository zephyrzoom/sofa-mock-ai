## 1. 交付物说明

| 交付物 | 说明 | 运行方式 |
|--------|------|----------|
| `mock-agent-1.0.0.jar` | Mock 拦截 Agent，非侵入式挂载到业务应用，拦截 HTTP 调用并返回预设响应 | 作为 `-javaagent` 参数挂载 |
| `mock-agent-server-1.0.0.jar` | 管理端服务：案例在线管理（Web 控制台 + REST API）、Agent 注册与监控 | `java -jar` 直接启动 |

可选附带：`mock-cases/` 示例案例目录（含 `user-query.json`）。

**两个交付物均可独立使用，也可配合使用：**

- 只用 `mock-agent`：从本地 `mock-cases/` 目录读取案例，纯本地 Mock。
- 只用 `mock-agent-server`：仅做案例的集中管理与分发，本身不拦截请求。
- 两者配合：业务应用挂 agent 后自动注册到 server、从 server 拉取案例，并在控制台查看 Agent 状态。

## 2. 环境要求

- **JDK 8 及以上**
- 无需额外安装第三方库：`mock-agent` 已将 ByteBuddy、Jackson 等依赖内置（shade 重定位），对业务应用的依赖无污染。

## 3. 快速开始（本地模式）

本地模式只用到 `mock-agent`：把案例文件放到本地目录，业务应用挂载 agent 后即可拦截。

### 3.1 准备 Mock Case 文件

新建目录（如 `mock-cases/`），放入 JSON 案例文件。示例 `mock-cases/user-query.json`：

```json
{
  "method": "POST",
  "path": "/user/query",
  "requestBody": "{\"uid\":1001}",
  "response": {
    "status": 200,
    "body": "{\"code\":1,\"name\":\"张三\"}"
  }
}
```

### 3.2 启动业务应用并挂载 Agent

在案例目录的上级目录执行（`-Dmock.cases.dir` 为相对路径，请保证工作目录正确）：

```bash
java -javaagent:mock-agent-1.0.0.jar \
     -Dmock.cases.dir=mock-cases \
     -Dmock.agent.autoRegister=false \
     -jar your-app.jar
```

> `-Dmock.agent.autoRegister=false` 表示关闭内置管理 API 与自动注册（纯本地模式更安静），完整配置见 [8. Agent 配置参考](#8-agent-配置参考)。

### 3.3 验证

应用内发出的、符合案例条件的 HTTP 调用（Feign / RestTemplate / Apache HttpClient / OkHttp）会被拦截并返回 mock 响应；不符合条件的请求正常放行到真实服务。

### 3.4 热更新

本地文件模式**每次请求都会重新读取**案例目录，修改或新增 `.json` 案例后**无需重启应用**，下一次请求立即生效；删除文件会自动移除对应案例。

## 4. 管理端服务 mock-agent-server

管理端是一个独立服务（默认端口 **8090**），提供：

- Web 管理控制台（Vue 3 + Element Plus）
- 案例的增删改查 / 批量导入 / 导出 / 启用停用
- Agent 实例在线监控
- REST API（供 Agent 拉取案例、上报心跳）

### 4.1 启动

```bash
java -jar mock-agent-server-1.0.0.jar
```

启动后：

| 地址 | 说明 |
|------|------|
| `http://localhost:8090/` | Web 管理控制台 |
| `http://localhost:8090/h2-console` | H2 数据库控制台 |

> 控制台前端依赖 unpkg CDN 加载 Vue / Element Plus，**需要联网**才能正常显示。

### 4.2 配置调整

管理端是标准 Spring Boot 应用，可用以下方式覆盖配置：

- 在 jar 同目录放一个 `application.yml`（覆盖内置配置）；
- 或用命令行参数，例如：
  ```bash
  java -jar mock-agent-server-1.0.0.jar --server.port=8080
  ```

常用配置项：

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `server.port` | `8090` | 服务端口 |
| `spring.datasource.url` | `jdbc:h2:file:./data/mock-agent-db` | H2 数据库文件路径（相对工作目录） |
| `spring.h2.console.enabled` | `true` | 是否开启 H2 控制台 |

> 数据存放在 `./data/mock-agent-db.mv.db`（默认相对启动目录），重启不丢失。

### 4.3 Web 控制台功能

| 菜单 | 功能 |
|------|------|
| **仪表盘** | 在线 Agent 数、案例总数、命中率等概览 |
| **案例管理** | 案例列表 / 搜索筛选 / 新增 / 编辑 / 删除 / 启停开关 / JSON 上传 / 导出 |
| **Agent 监控** | 已注册的 Agent 实例、在线状态、心跳 |

案例编辑支持**表单模式**和 **JSON 模式**；JSON 上传接受案例数组文件。

## 5. Agent 与 Server 联动

让业务应用从管理端拉取案例并自动注册、接受监控，只需挂载 agent 时**保持默认配置**（不设置 `-Dmock.agent.autoRegister=false`）：

```bash
java -javaagent:mock-agent-1.0.0.jar \
     -Dmock.agent.server.url=http://localhost:8090 \
     -jar your-app.jar
```

联动流程：

1. **注册**：agent 启动时自动把自身实例（appName、instanceId、IP、内置管理 API 端口）注册到 server。
2. **心跳**：每 30 秒上报一次心跳（注册失败自动重试）。
3. **拉取远程案例**：首次拦截到请求时，从 `/api/apps/{appName}/cases/json` 拉取该应用已启用的案例。本地案例与远程案例**合并**使用。
4. **实时监控**：agent 内置管理 API 暴露匹配统计与事件流（见 [10](#10-agent-内置管理-api)）。

**应用名（appName）识别**：用于注册与拉取案例，自动检测顺序：

1. 系统属性 `mock.agent.server.appName`
2. `spring.application.name` 系统属性
3. 环境变量 `SPRING_APPLICATION_NAME`
4. classpath 下 `application.yml` / `application.yaml` / `application.properties` / `bootstrap.yml` 中的 `spring.application.name`
5. 都取不到则用默认值 `default`

管理端里为某个应用配置案例时，案例的 `appName` 必须与该值一致，agent 才能拉到。

## 6. Mock Case 格式参考

### 6.1 本地 JSON 文件格式

本地文件采用"嵌套 `response`"结构：

```json
{
  "method": "POST",
  "path": "/user/query",
  "requestBody": "{\"uid\":1001}",
  "pathPattern": "/user/**",
  "matchType": "ANT",
  "condition": "body.uid == 1001",
  "requestHeaders": { "X-Env": "test" },
  "response": {
    "status": 200,
    "body": "{\"code\":1,\"name\":\"张三\"}"
  },
  "responseHeaders": { "Content-Type": "application/json" },
  "delayMs": 100,
  "description": "用户查询",
  "enabled": true,
  "priority": 0
}
```

### 6.2 字段说明

| 字段 | 必填 | 类型 | 说明 |
|------|------|------|------|
| `method` | ✅ | string | HTTP 方法（GET/POST/PUT/DELETE 等） |
| `path` | ✅ | string | 请求路径（参与案例索引，见 [7.1](#71-路径匹配)） |
| `response.status` | ✅ | int | 响应状态码 |
| `response.body` | ✅ | string | 响应体（JSON 字符串） |
| `requestBody` | 否 | string | 请求体条件，JSON 字符串，支持**部分字段匹配**（见 [7.2](#72-请求体部分匹配)） |
| `pathPattern` | 否 | string | `matchType` 为 REGEX / ANT 时使用的匹配模式 |
| `matchType` | 否 | string | `EXACT`（默认）/ `REGEX` / `ANT` |
| `condition` | 否 | string | 条件表达式（见 [7.3](#73-条件表达式)） |
| `requestHeaders` | 否 | object | 请求头匹配条件（**当前不生效**，见 [11. 已知限制](#11-已知限制)） |
| `responseHeaders` | 否 | object | mock 响应头（**当前不生效**，见 [11](#11-已知限制)） |
| `delayMs` | 否 | long | 模拟响应延迟毫秒数（**当前不生效**，见 [11](#11-已知限制)） |
| `description` | 否 | string | 案例描述 |
| `enabled` | 否 | boolean | 是否启用，默认 `true` |
| `priority` | 否 | int | 优先级，数值越大越优先匹配，默认 `0` |

### 6.3 管理端 REST / 上传格式

通过管理端 REST API（`POST /api/cases`、`POST /api/cases/upload`）时，`status` / `body` 是**顶层字段**，且可带 `appName`：

```json
{
  "appName": "demo",
  "method": "POST",
  "path": "/user/query",
  "requestBody": "{\"uid\":1001}",
  "status": 200,
  "body": "{\"code\":1,\"name\":\"张三\"}",
  "matchType": "EXACT",
  "enabled": true,
  "priority": 0
}
```

Agent 从 `/api/apps/{appName}/cases/json` 拉取时，server 会自动转换回 `response:{status,body}` 嵌套格式。

## 7. 匹配规则

### 7.1 路径匹配

案例在内存中按 **`method + path` 精确键**建立索引，请求进来时先取相同键下的候选案例，再在候选内部按类型匹配：

| matchType | 说明 |
|-----------|------|
| `EXACT`（默认） | `path` 与请求路径完全相等即命中 |
| `REGEX` | 用 `pathPattern` 作为正则，对请求路径做**整串匹配** |
| `ANT` | 用 `pathPattern` 按 Ant 风格匹配，支持 `*`（单段）、`**`（多段）、`{var}`（占位）、`?`（单字符） |

> ⚠️ 因为候选按 `method + path` 精确索引，`REGEX` / `ANT` 目前**不能跨多个不同路径生效**（例如请求 `/user/123` 不会命中 `path=/user/{id}` 的案例），仅用于同一 `path` 下多案例的区分。详见 [11. 已知限制](#11-已知限制)。

### 7.2 请求体部分匹配

`requestBody` 条件为 JSON 字符串时，只要**实际请求体包含条件中的所有字段且值相等**即命中（支持嵌套对象）：

条件 `{"uid":1001}` 可命中以下任一请求体：
- `{"uid":1001}`
- `{"uid":1001,"extra":"field"}`
- `{"uid":1001,"nested":{"key":"value"}}`

若条件或请求体不是合法 JSON，则退化为**字符串完全相等**。

### 7.3 条件表达式

`condition` 支持更灵活的表达式，操作符：`&&`、`||`、`==`、`!=`、`contains`、`matches`。值引用：

- 字符串字面量：`'abc'` 或 `"abc"`
- 请求体顶层字段：`body.uid`
- 请求头：`headers['X-Env']` 或 `headers["X-Env"]`（当前请求头未透传，恒为空，见 [11](#11-已知限制)）

示例：

```
body.uid == 1001 && body.role != 'admin'
headers['X-Env'] contains 'test'
body.name matches '张.*'
```

### 7.4 优先级与匹配顺序

- 候选案例按 `priority` **降序**排序，优先尝试优先级高的。
- 每个候选须同时满足：**路径匹配（任一类型命中）+ 请求体 + 条件 + 请求头**，才被选中。
- `enabled=false` 的案例直接跳过。
- 所有候选都不满足时，**放行真实调用**。

## 8. Agent 配置参考

以下均为 JVM 系统属性（挂载时用 `-Dxxx=yyy` 传入）：

| 系统属性 | 默认值 | 说明 |
|---------|--------|------|
| `mock.cases.dir` | `mock-cases` | 本地 Mock Case 文件目录 |
| `mock.agent.debug` | `false` | 是否启用调试日志 |
| `mock.agent.log.level` | `INFO` | 日志级别：`OFF` / `ERROR` / `WARN` / `INFO` / `DEBUG` |
| `mock.agent.bytebuddy.debug` | `false` | 是否输出 ByteBuddy 插桩调试信息 |
| `mock.agent.server.url` | `http://localhost:8090` | 管理端地址（注册、心跳、远程案例） |
| `mock.agent.server.appName` | 自动检测 | 应用名（见 [5](#5-agent-与-server-联动) 的检测顺序） |
| `mock.agent.api.port` | 自动随机 | Agent 内置管理 API 端口；未设置时随自动注册随机分配 |
| `mock.agent.autoRegister` | `true` | 是否自动启动内置管理 API 并注册到 server；设为 `false` 则关闭，适合纯本地模式 |

## 10. Agent 内置管理 API

挂载 agent 后（`autoRegister=true` 或设置了 `mock.agent.api.port`），agent 内置一个轻量 HTTP 管理接口。端口：设置了 `mock.agent.api.port` 用指定端口，否则为随机端口（可在管理端 Agent 列表中查看）。

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/mock/cases` | 列出当前加载的所有案例 |
| POST | `/mock/cases/reload` | 强制重新加载全部案例（本地 + 远程） |
| GET | `/mock/status` | 健康状态 |
| GET | `/mock/stats` | 统计概览（总请求数、命中数、透传数、命中率等） |
| GET | `/mock/events` | 最近最多 100 条匹配事件 |
| GET | `/mock/events/stream` | SSE 实时事件流 |

## 11. 已知限制

1. **候选按 `method + path` 精确索引**：`REGEX` / `ANT` 路径模式只能在"同一 `path` 下的候选"之间区分，**不能跨多个动态路径命中**。
2. **`requestHeaders` 请求头匹配不生效**：匹配器已实现，但拦截器暂未把真实请求头传入匹配上下文，请求头条件恒不命中。
3. **`responseHeaders`、`delayMs` 未应用**：字段会被解析和存储，但响应构造器目前只使用 `status + body`。
4. **本地案例每请求重读**：文件模式每次请求都会重新扫描目录，文件较多时有 IO 开销（测试场景可接受）。
5. **控制台需联网**：管理端前端通过 unpkg CDN 加载 Vue / Element Plus，离线环境无法正常显示界面（REST API 不受影响）。
6. **agent 与 server 默认同机**：`mock.agent.server.url` 默认指向 `localhost:8090`，跨机部署需显式配置。

## 12. 常见问题（FAQ）

**Q1：请求没有被 mock，走了真实调用？**
- 先确认案例的 `method`、`path` 与请求一致（候选是精确键）。
- 再确认请求体是否满足 `requestBody` / `condition` 条件（见 [7](#7-匹配规则)）。
- 打开调试日志定位：`-Dmock.agent.debug=true -Dmock.agent.log.level=DEBUG`，观察 `match failed` / `no match` 日志。

**Q2：怎么确认 agent 是否加载了案例？**
- 保持默认注册配置，在管理端"Agent 监控"里查看；或直接访问 agent 内置 API：`curl http://localhost:<port>/mock/cases`。
- 日志中会有 `loaded mock case: POST /user/query from user-query.json`。

**Q3：没设置 `mock.agent.api.port`，怎么知道内置管理端口？**
- 未指定时端口随机，可在管理端 Agent 列表查看，或看启动日志 `Management API started on port <port>`。也可显式指定：`-Dmock.agent.api.port=8899`。

**Q4：如何彻底关闭 agent 的自动注册 / 内置 API？**
- 加 `-Dmock.agent.autoRegister=false`，且不设置 `mock.agent.api.port`。

**Q5：管理端数据存在哪里？**
- 默认在工作目录下 `data/mock-agent-db.mv.db`（H2 文件数据库），重启不丢失。

**Q6：改了案例文件但没生效？**
- 本地文件模式每次请求都会重读，确认文件放在 `-Dmock.cases.dir` 指向的目录、文件名以 `.json` 结尾、JSON 合法。修改后发一次新请求即可，无需重启。
